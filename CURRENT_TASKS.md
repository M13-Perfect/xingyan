## 2026-07-01 回访时限（revisit deadline grace period）

Before this, "已逾期" had NO grace period at all in either place it was computed: the per-row frontend tag ([App.vue](xyyx/xyyx-frontend/src/App.vue) `revisitTag`) and the backend header count ([SurveyController.getRevisitCount](xyyx/src/main/java/org/example/xyyx/controller/SurveyController.java:267)) both flagged a record overdue the instant its `next_survey_date`'s calendar day was in the past. User confirmed via design review (calendar-day precision, no visible "grace" state, deadline minimum 1 day, no 0) before implementation:

- New tenant-wide setting `revisit_deadline_days` (default 3, range 1-30) added to `tenant_system_settings` via `db/migrations/V20260701_002_add_revisit_deadline_days.sql` (idempotent add-column + CHECK, mirrors the `chk_tenant_system_order_page_size` pattern) + `db/verify/V20260701_verify_revisit_deadline_days.sql`. **Not yet applied to any live DB** (local or VPS) — matches the manual-migration pattern already used for phone privacy/system settings; run it before relying on a non-default deadline.
- `TenantSystemSettingsService`: `TenantSystemSettings` record gained `revisitDeadlineDays`; `getEffectiveSettings`/`updateSettings`/`defaults()`/audit log all carry it; validated 1-30 via `clampRevisitDeadlineDays` (renamed old `clamp` to `clampOrderPageSize` for clarity, no behavior change there).
- `SurveyController.getRevisitCount`: overdue cutoff is now `todayStart.minusDays(revisitDeadlineDays)` instead of `todayStart` — the counting SQL itself is unchanged, only the cutoff instant passed in shifted. `getAppSettings` now also returns `revisitDeadlineDays` for ordinary (non-admin) frontend use.
- Frontend: extracted the previously-inline `stripTime`/`formatRevisitDate`/`revisitTag` helpers out of `App.vue` into a new pure module `xyyx/xyyx-frontend/src/revisit.js` (mirrors the existing `phonePrivacy.js` extraction pattern) so the day-math has real unit tests (`revisit.test.js`, 7 tests) instead of only source-regex checks. `revisitTag` now takes `revisitDeadlineDays` and only returns `overdue` once `daysPast > revisitDeadlineDays`; a record past its date but still inside the grace window renders no tag at all (same as a future date), per user's explicit choice. New "回访时限（天）" number input added to the 系统设置 modal next to 单页显示订单数量, loaded/saved through the existing `/api/admin/system-settings` GET/PUT and `/api/app-settings` endpoints — no new endpoints.

- 2026-07-01 **real bug found and fixed** via live debugging with the user (72 待回访 counted correctly by the backend, but zero rows ever rendered red): `GET /api/surveys` serializes `nextSurveyDate` through [SurveyPhoneDisplayService.java:160](xyyx/src/main/java/org/example/xyyx/service/SurveyPhoneDisplayService.java:160) (`row.put("nextSurveyDate", survey.getNextSurveyDate())`), which puts the raw `LocalDateTime` into a `Map<String,Object>` — this **loses** the `Survey` entity's `@JsonFormat(pattern="yyyy-MM-dd HH:mm")` annotation (that annotation only applies when Jackson serializes the `Survey` bean directly, not a Map holding the same value), so the real wire format is ISO `"2026-06-24T21:59:00"`, not the space-separated format `revisit.js`'s `stripTime` assumed (`d.split(' ')[0]`). Splitting on a space that never appears left the full `"...T00:00:00"` suffix in `ymd`, which then never `===` nor `<` a plain `YYYY-MM-DD` `todayDate` (a longer string sharing the same prefix compares as *greater*, not less, in JS) — so `revisitTag` silently fell through to `{type: null}` for every single row, regardless of how overdue it was. The backend's separately-computed `/api/surveys/revisit-count` badge numbers were unaffected (pure SQL, no JSON round-trip), which is why the counts looked right while zero rows were tagged.

  - Verified: frontend `npm test` (31/31), `npm run build`, confirmed via `curl` the running dev server picked up the fix, and the user confirmed in their own browser after a hard refresh that red "已逾期 N 天" tags now render correctly.
